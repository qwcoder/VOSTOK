# Протокол обмена ShelfVostok <-> контроллер ТРК

Восстановлено статическим реверсом `ShelfVostok.exe` (Ghidra, декомпиляция от
точек вызова `WriteFile`/`Cport@TCustomComPort@WriteAsync` вверх по графу
вызовов). Бинарник собран с отладочными именами методов и русско/англоязычными
строками логов — они и позволили точно, без единого захвата трафика с реального
порта, восстановить структуру кадра, чек-сумму и таблицу команд.

Ключевые адреса в `ShelfVostok.exe` (build 2019-07-28, PE32 i386):
- `0x004a8a8c` — низкоуровневый обмен "отправить кадр, дождаться и разобрать ответ"
- `0x004a8a34` — чек-сумма
- `0x004a9608` — чтение N байт с таймаутом (через `Cport.ReadAsync`+`WaitForAsync`)

## Физический уровень

RS-485, half-duplex. Перед передачей поднимается RTS
(`Cport.TCustomComPort.SetRTS(...,1)`), после — опускается. Между передачей и
чтением ответа выдерживается пауза, вычисляемая из скорости порта (в бинарнике
зашита таблица коэффициентов на 13 стандартных скоростей — от подстановки в
`switch` видно, что это индекс из `TBaudRate` компонента ComPort).

Скорость по умолчанию (из `ShelfVostok.INI`): **19200 8N1**, без аппаратного
управления потоком (RTS используется программно самим протоколом, не как
hardware flow control).

## Формат кадра

```
байт 0:        0x2D  ('-')      — маркер начала кадра
байт 1:        адрес ТРК        — из конфигурации канала (аналог MPort/адрес)
байт 2:        счётчик/seq      — побайтовый счётчик обменов с данным устройством
                                   (поле "device+0x41", инкрементируется на каждый обмен)
байт 3:        длина кадра N    — используется и при разборе ответа, и в чек-сумме
байт 4:        код команды
байты 5..N-3:  параметры команды (0..N байт, little-endian для чисел)
байты N-2,N-1: CRC-16, big-endian
```

Приёмник (тот же формат для ответа) читает: 1 байт (сверка с `'-'`), затем ещё
4 байта заголовка (адрес+seq+длина+код), затем `длина-5` оставшихся байт полезной
нагрузки+CRC.

## Чек-сумма — CRC-16/XMODEM

`FUN_004a8a34`: полином `0x1021`, начальное значение `0`, без входного/выходного
отражения битов (MSB-first), без финального XOR. Считается по всем байтам кадра
кроме двух байт самой CRC (`длина - 2` байт). Классический CRC-16/XMODEM.

```c
uint16_t crc16_xmodem(const uint8_t *data, int len) {
    uint16_t crc = 0;
    for (int i = 0; i < len; i++) {
        crc ^= (uint16_t)data[i] << 8;
        for (int b = 0; b < 8; b++)
            crc = (crc & 0x8000) ? (crc << 1) ^ 0x1021 : (crc << 1);
    }
    return crc; // пишется в кадр big-endian
}
```

## Адресация ТРК/пистолетов в памяти приложения

Везде встречается одна и та же арифметика индекса в глобальных массивах
конфигурации/состояния устройств:

```
index = TRK_ID * 0x1b20 + Half * 0xd70 + Pistolet * 600
```

Совпадает с полями `TRKID`/`Half`/`HorPos`/`VerPos` из схемы `tabTRK`
(восстановлена ранее из строк `CREATE TABLE`). Границы циклов в коде — до 2
"половин" (`Half`) и до 5 пистолетов на ТРК.

## Надёжность обмена

- Retry: как правило 5 попыток (у 0x0A — 10), с логированием `ERROR` в
  внутренний лог на каждую неудачу.
- При неответе более 3 обращений — в UI ошибка "Нет ответа от контроллера ТРК
  после трех обращений".

## Не восстановлено / следующие шаги

- Протокол уровнемера (`tabLevelMeters`) — отдельная задача, использует,
  вероятно, тот же низкоуровневый `FUN_004a8a8c`, но другую адресацию
  (по цистернам, не по ТРК/пистолетам). Не искали отдельно.
- Точные коды команд "Пауза/Старт/Стоп ТРКрана" и "Чтение данных за смену".
- Единицы измерения price/density/pressure полей (масштаб, знак).
